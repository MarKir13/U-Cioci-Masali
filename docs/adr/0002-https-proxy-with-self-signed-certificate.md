# 0002. HTTPS through an nginx proxy with a self-signed certificate

- Status: Accepted
- Date: 2026-11-07
- Authors: Jakub Rachubka

## Context

Requirement W3.3 [K] says the shop must serve traffic only over HTTPS, with a certificate we
generate and sign ourselves, and redirect HTTP requests to HTTPS with 301. W3.2 [K] adds that the
instructor starts the shop from a clean clone with one command, so the certificate cannot be a
manual step, and the private key must not be committed.

The shop runs on the official image `prestashop/prestashop:8.2.8-8.1-apache` (plain HTTP on port
80). PrestaShop stores its domain and SSL flags in the database at install time, and it decides
whether a request is secure from `$_SERVER['HTTPS']`.

Three things had to be decided: where TLS ends, where and when the certificate is made, and how
the redirect keeps the published port (the shop runs on `localhost:8443`, not on 443).

## Options considered

### Where TLS ends

**Separate nginx proxy container (chosen)**

- Pro: the shop image stays the official one plus our files; TLS config is in one small file.
- Pro: only the proxy publishes ports, so the shop cannot be reached over HTTP by mistake.
- Pro: HTTP/2 and the redirect are a few lines of nginx config that are easy to explain.
- Con: one more container, and the shop has to be told the request was HTTPS
  (`X-Forwarded-Proto` → `HTTPS=on` in Apache), otherwise PrestaShop loops on redirects.
- Con: nginx limits must match `php.ini` (upload size, timeout), or uploads fail with 413 and
  long admin actions with 504.

**mod_ssl in the shop container**

- Pro: no extra container, no forwarded headers.
- Con: we would change the Apache vhosts of the official image and generate the cert inside its
  start scripts, which mixes TLS with the PrestaShop install logic.
- Con: the HTTP → HTTPS redirect with the published port would be in Apache rewrite rules next to
  PrestaShop's own `.htaccess`, harder to read and to test.

### Where and when the certificate is generated

**On proxy start, into a named volume, only if missing (chosen)**

- Pro: no manual step and no key in git; `down` / `up` keeps the same cert, so a browser
  exception the user accepted stays valid; `down -v` gives a fresh one.
- Pro: uses the image's own hook (`/docker-entrypoint.d/15-generate-cert.sh`, run before
  the config template is rendered), so no custom entrypoint.

**At image build time**

- Con: the private key would be baked into the image layers; every rebuild changes the cert.

**Generated by a script before `docker compose up`**

- Con: an extra manual step, different on Windows and Linux; breaks W3.2.

The certificate is a self-signed leaf (CN `localhost`, SAN `DNS:localhost`, `IP:127.0.0.1`,
RSA 2048, 825 days). A private CA would let us trust it once in the OS, but nobody needs that for
a local project and it is one more thing to explain.

### How the redirect keeps the port

nginx `$host` has no port, so `return 301 https://$host$request_uri` would send users to
`https://localhost/...` (port 443), where nothing listens. The config is a template rendered by
the nginx image's envsubst at start, and the redirect is
`https://$host:${HTTPS_PORT}$request_uri`. envsubst replaces only variables that are defined in
the environment, so `$host` and `$request_uri` stay nginx variables. Towards the shop the proxy
sends `Host $http_host`, which keeps the port, so PrestaShop sees `localhost:8443`, the same as
`PS_DOMAIN`.

## Decision

A `proxy` service built from `deploy/proxy/` (nginx 1.28.0 alpine + openssl) publishes
`HTTP_PORT` (301 to HTTPS) and `HTTPS_PORT` (TLS, HTTP/2, proxy to `shop:80`). The shop has no
published ports, is installed with `PS_ENABLE_SSL=1` and `PS_DOMAIN=localhost:${HTTPS_PORT}`, and
Apache maps `X-Forwarded-Proto: https` to `HTTPS=on`. No HSTS, because a self-signed cert on
`localhost` would force HTTPS on every other local project in the browser.

## Consequences

- Browsers show a certificate warning on first visit; tools need `curl -k`, Lighthouse with the
  ignore-certificate flag (M-W3.9) and Playwright with `ignoreHTTPSErrors: true`.
- Existing installs must be reinstalled once (`down -v`), because the domain and SSL flags live
  in the database volume; local `deploy/.env` files need `HTTP_PORT` / `HTTPS_PORT` instead of
  `SHOP_PORT`.
- If `upload_max_filesize` or `max_execution_time` in `shop/config/php.ini` change,
  `client_max_body_size` and `proxy_read_timeout` in `deploy/proxy/default.conf.template` must
  change with them.
- The smoke test (#17) and E2E tests (W4) must use the HTTPS URL and accept the self-signed cert.
